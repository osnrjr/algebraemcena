Instalação.

🌐 PARTE 1: Configuração no Host (No PowerShell do Windows)

Esta parte é executada UMA ÚNICA VEZ por máquina (Doc ① §1). Repita somente ao configurar uma
máquina nova, ao reconstruir o WSL ou ao alterar deliberadamente o padrão global de infraestrutura.
Nunca a repita a cada novo projeto Django.

Abra o PowerShell como Administrador para instalar a base do sistema e as ferramentas de interface do Windows:

# 1. Instalar o WSL com Ubuntu e verificar
wsl --install -d Ubuntu
wsl --version

# 2. Instalar o Git no Windows (Útil para projetos locais do Windows)
winget install --id Git.Git -e --source winget
git --version

# 3. Instalar o VS Code no Windows e a extensão oficial do WSL
winget install --id Microsoft.VisualStudioCode -e --source winget
code --version
code --install-extension ms-vscode-remote.remote-wsl

# (OPCIONAL — fora do escopo mínimo, Doc ① §1.1) Ferramentas adicionais de CLI de terceiros.
# O padrão global não exige nenhuma. Exemplo usado no processo original (Antigravity CLI):
# irm https://antigravity.google/cli/install.ps1 | iex
# antigravity --version


🐧 PARTE 2: Configuração e Desenvolvimento (No Terminal do Ubuntu/WSL)
A partir aqui, feche o PowerShell. Abra o aplicativo Ubuntu no seu menu iniciar do Windows. 
Todos os comandos abaixo devem ser rodados dentro do terminal Linux.

Passo 2.1: Instalação das ferramentas nativas no Linux

# 1. Atualizar o sistema e instalar Python, PIP, Venv, compiladores e o Git do Linux
sudo apt update && sudo apt upgrade -y
sudo apt install python3 python3-pip python3-venv python3-dev build-essential git -y

# 2. Configurar a identidade do seu Git no Linux (Obrigatório para fazer Commits)
# ATENÇÃO: use o alias mascarado no-reply do GitHub, nunca um e-mail pessoal — obtenha o seu em
# GitHub > Settings > Emails > Keep my email address private.
# Formato do alias: ID+seu-usuario@users.noreply.github.com
git config --global user.name "Seu Nome de Usuário GitHub"
git config --global user.email "SEU_ID+seu-usuario@users.noreply.github.com"

# 3. Verificar a identidade ativa (Doc ① §5.3) — repita antes de commitar em máquina ou clone novo
git config user.email
# O endereço retornado DEVE conter users.noreply.github.com. Se vier vazio ou com e-mail pessoal,
# pare e corrija antes de qualquer commit.

Passo 2.2: Criando a estrutura do projeto Django no Linux/WSL
Navegue até a pasta dedicada ao ecossistema Django dentro do seu diretório home:

# 4. Criar a pasta do seu projeto dentro do ecossistema Django e entrar nela
#    (nunca solta em ~/projetos/ e nunca dentro de /mnt/c/ — Doc ① §2.1)
mkdir -p ~/projetos/django/meu_projeto_django
cd ~/projetos/django/meu_projeto_django

# 5. Criar o Ambiente Virtual (.venv) usando o Python do Linux
python3 -m venv .venv

# 6. Ativar o ambiente virtual no Linux
source .venv/bin/activate

# (O seu terminal agora mostrará (.venv) no início da linha)

---

Passo 2.3: Instalação do Django e Criação do Projeto

# 7. Atualizar o gerenciador de pacotes interno e instalar o conjunto-base de dependências
pip install --upgrade pip
pip install django django-environ argon2-cffi

# django-environ → leitura tipada do .env (Doc ① §4.4)
# argon2-cffi    → hasher de senhas Argon2id (Doc ① §16.1); dependência "sempre" do ecossistema (§22.2)
# Outras dependências do padrão (cryptography, django-allauth etc.) só entram quando o projeto
# precisar e sempre com justificativa (Doc ① §7.7 e §22.2).

---

# 8. Criar o projeto Django (Isso vai gerar o settings.py automaticamente)

django-admin startproject meu_site .

# ⚠️ NOTA: O ponto "." no final é crucial. Ele diz para o Django criar 
# os arquivos direto na raiz atual, mantendo a estrutura limpa que planejamos.
# ⚠️ NOTA: evite chamar o pacote de configuração de "core": esse é o nome da app transversal
# do catálogo de apps do ecossistema (apps/core, Doc ① §9.4).

python -m django --version

# Confira a versão instalada: a partir do Django 6.0 a CSP é nativa; abaixo disso é preciso a
# dependência django-csp (Doc ① §14.3 e §22.2). A versão fica fixada no requirements.txt.


Passo 2.4: Segurança, Git e Requirements (Na raiz do projeto)

# 9. Inicializar o repositório Git do projeto (Doc ① §23.1)
git init -b main

# 10. Criar o arquivo .gitignore completo (ANTES do primeiro "git add" — Doc ① §4.7)
cat << 'EOF' > .gitignore
.venv/
.env
*.pyc
__pycache__/
*.log
.DS_Store
media/
staticfiles/
db.sqlite3
EOF

# (db.sqlite3 entra porque o banco local é SQLite. O restante é o conjunto mínimo global do Doc ① §4.7.)

# Verificar se gravou corretamente
cat .gitignore

# 11. Criar o .env.example (versionado): somente os NOMES das variáveis, sem valores reais
#     Conjunto-base do ecossistema (Doc ① §4.6 e §18.4). O .env.example completo do projeto está
#     no Anexo B do PROJECT_SPEC.md (inclui TENANCY_MODE, OAuth e webhooks).
cat << 'EOF' > .env.example
SECRET_KEY=
DEBUG=False
ALLOWED_HOSTS=
CSRF_TRUSTED_ORIGINS=
ADMIN_URL=
FIELD_ENCRYPTION_KEY=
JWT_SIGNING_KEY=
EMAIL_HOST=
EMAIL_HOST_USER=
EMAIL_HOST_PASSWORD=
EOF

# 12. Criar o arquivo .env físico (local, NÃO versionado) com valores iniciais
# ATENÇÃO: substitua o valor de SECRET_KEY abaixo por uma chave gerada aleatoriamente para ESTE
# projeto — nunca reaproveite o valor de exemplo. Gere com:
# python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
cat << 'EOF' > .env
SECRET_KEY=SUBSTITUA_POR_UMA_CHAVE_UNICA_GERADA_LOCALMENTE
DEBUG=True
EOF

# Sempre que uma nova variável for adicionada ao projeto, atualize o .env.example no mesmo commit.

# Chaves adicionais — somente quando o projeto as utilizar (Doc ① §18.4 e §23.4).
# Devem ser DISTINTAS entre si e da SECRET_KEY, geradas localmente e guardadas só no .env:
#   FIELD_ENCRYPTION_KEY (Fernet; requer o pacote cryptography instalado no .venv):
#     python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
#   JWT_SIGNING_KEY (≥ 32 bytes aleatórios; apenas se houver JWT):
#     python -c "import secrets; print(secrets.token_urlsafe(48))"

# 13. Gerar o arquivo requirements.txt na raiz do projeto
pip freeze > requirements.txt

# (Sempre que instalar um pacote novo, rode "pip freeze > requirements.txt" de novo,
#  no mesmo commit que introduziu a dependência.)

Passo 2.5: Abrindo o projeto no VS Code do Windows

code .

🛠️ PARTE 3: Integração do django-environ no Código e Baseline de Settings
Com o VS Code aberto através do WSL, 
navegue até o arquivo gerado automaticamente meu_site/settings.py e substitua o bloco do topo pelo código abaixo:

---
import environ
from pathlib import Path

# Define a raiz do projeto (onde está o arquivo .env)
BASE_DIR = Path(__file__).resolve().parent.parent

# Inicializa o leitor de variáveis de ambiente com tipo booleano padrão para o DEBUG
env = environ.Env(
    DEBUG=(bool, False)
)

# Faz a leitura do arquivo .env localizado na raiz do projeto
environ.Env.read_env(BASE_DIR / '.env')

# Substitua as linhas originais do Django por estas que lêem o arquivo oculto de forma tipada:
SECRET_KEY = env('SECRET_KEY')
DEBUG = env.bool('DEBUG', default=False)

---

⚠️ ATENÇÃO: apague do settings.py gerado as linhas originais "SECRET_KEY = 'django-insecure-...'",
"DEBUG = True" e "ALLOWED_HOSTS = []" (e a definição duplicada de BASE_DIR). Se ficarem mais abaixo
no arquivo, elas SOBRESCREVEM os valores lidos do .env.

Passo 3.1: Baseline de segurança do settings (Doc ① §12.3)

A versão 3.1 do padrão exige o baseline de segurança desde o início do projeto, não só no deploy.
Acrescente abaixo do bloco anterior (os valores já são seguros por padrão; DEBUG=True só vale no local):

---
ALLOWED_HOSTS = env.list('ALLOWED_HOSTS', default=[])           # nunca ['*'] fora do local
CSRF_TRUSTED_ORIGINS = env.list('CSRF_TRUSTED_ORIGINS', default=[])  # com esquema: https://dominio

# Transporte (HTTPS)
SECURE_SSL_REDIRECT = env.bool('SECURE_SSL_REDIRECT', default=not DEBUG)
SECURE_HSTS_SECONDS = env.int('SECURE_HSTS_SECONDS', default=0 if DEBUG else 3600)  # elevar até 31536000
SECURE_HSTS_INCLUDE_SUBDOMAINS = env.bool('SECURE_HSTS_INCLUDE_SUBDOMAINS', default=False)
SECURE_HSTS_PRELOAD = env.bool('SECURE_HSTS_PRELOAD', default=False)

# Cookies, sessão e CSRF
SESSION_COOKIE_SECURE = not DEBUG
CSRF_COOKIE_SECURE = not DEBUG
SESSION_COOKIE_HTTPONLY = True
SESSION_COOKIE_SAMESITE = 'Lax'
CSRF_COOKIE_SAMESITE = 'Lax'

# Cabeçalhos (declarados explicitamente, mesmo coincidindo com defaults do Django)
SECURE_CONTENT_TYPE_NOSNIFF = True
X_FRAME_OPTIONS = 'DENY'
SECURE_REFERRER_POLICY = 'same-origin'
SECURE_CROSS_ORIGIN_OPENER_POLICY = 'same-origin'

# Limites de entrada (Doc ① §15.4)
DATA_UPLOAD_MAX_MEMORY_SIZE = env.int('DATA_UPLOAD_MAX_MEMORY_SIZE', default=1_048_576)  # 1 MiB
DATA_UPLOAD_MAX_NUMBER_FIELDS = env.int('DATA_UPLOAD_MAX_NUMBER_FIELDS', default=500)
---

Regras que acompanham o baseline:
 - Os middlewares gerados pelo startproject (SecurityMiddleware, SessionMiddleware, CsrfViewMiddleware,
   AuthenticationMiddleware, XFrameOptionsMiddleware) NÃO podem ser removidos (Doc ① §12.2).
 - Não crie linhas vazias no .env para as variáveis numéricas acima (ex.: "SECURE_HSTS_SECONDS="):
   o valor vazio quebra a conversão de tipo. Se não for sobrescrever, simplesmente não declare.
 - Ajustes de produção (HSTS elevado, proxy reverso, CSP etc.) não pertencem a este roteiro: os valores
   e as exceções do projeto ficam no PROJECT_SPEC.md §10 (Doc ① §12.3 e §14).

Confirme que o settings.py continua válido:

python manage.py check

🌐 PARTE 4: Estrutura Modular, Usuário Customizado e Inicialização do Servidor

⚠️ MUDANÇA DA v3.1: em projeto NOVO, a primeira migração NÃO é mais o primeiro comando depois do
startproject. O usuário customizado com chave UUID (AUTH_USER_MODEL) precisa existir ANTES da primeira
migração — alterá-lo depois é custoso (Doc ① §10.4 e §23.4). A ordem correta é:

   apps → usuário customizado e Argon2id → makemigrations → migrate → createsuperuser → runserver

Com o ambiente virtual ativo (.venv) no terminal:

Passo 4.1: Criar as apps-base dentro de apps/ (Doc ① §9.2 e §9.4)

# 1. Criar o pacote apps/ e as duas apps-base do ecossistema
mkdir -p apps/core apps/accounts
touch apps/__init__.py
python manage.py startapp core apps/core
python manage.py startapp accounts apps/accounts

# 2. Em apps/core/apps.py e apps/accounts/apps.py, troque o "name" gerado:
#      name = 'apps.core'          (e)          name = 'apps.accounts'
#    Cada app terá um README.md próprio (Doc ① §9.3): crie apps/core/README.md e apps/accounts/README.md.

# apps/core/models.py — modelo-base com UUIDv4 (Doc ① §10.4)
---
import uuid
from django.db import models

class UUIDModel(models.Model):
    id = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)

    class Meta:
        abstract = True
---

# apps/accounts/models.py — usuário customizado com chave UUID
---
from django.contrib.auth.models import AbstractUser
from apps.core.models import UUIDModel

class User(UUIDModel, AbstractUser):
    pass
---

# apps/accounts/admin.py — registrar o usuário no Admin
---
from django.contrib import admin
from django.contrib.auth.admin import UserAdmin
from .models import User

admin.site.register(User, UserAdmin)
---

Passo 4.2: Ajustes finais no settings.py e no urls.py

# Em meu_site/settings.py:
---
INSTALLED_APPS = [
    # ... apps padrão do Django, sem remover nenhuma ...
    'apps.core',
    'apps.accounts',
]

AUTH_USER_MODEL = 'accounts.User'          # ANTES da primeira migração

# Argon2id em primeiro lugar (Doc ① §16.1); os demais permitem migrar hashes antigos no próximo login
PASSWORD_HASHERS = [
    'django.contrib.auth.hashers.Argon2PasswordHasher',
    'django.contrib.auth.hashers.PBKDF2PasswordHasher',
    'django.contrib.auth.hashers.PBKDF2SHA1PasswordHasher',
]

ADMIN_URL = env('ADMIN_URL')               # URL do Admin não padrão (Doc ① §11.3)
---

# Em meu_site/urls.py, troque path('admin/', ...) por:
---
from django.conf import settings
from django.contrib import admin
from django.urls import path

urlpatterns = [
    path(settings.ADMIN_URL, admin.site.urls),
]
---

# Adicione ADMIN_URL ao .env local (valor NÃO padrão, terminado em "/"). Sugestão de geração:
# python -c "import secrets; print('painel-' + secrets.token_urlsafe(8) + '/')"
# Exemplo de linha no .env:  ADMIN_URL=painel-AbC123xY/
# (A variável já consta no .env.example criado no Passo 2.4.)

Passo 4.3: Primeira migração e inicialização

# 1. Gerar a migração inicial do usuário customizado (cria apps/accounts/migrations/0001_initial.py,
#    que DEVE ser versionada no Git junto com o código)
python manage.py makemigrations

# 2. Executar as migrações iniciais do banco de dados padrão (SQLite)
python manage.py migrate

# 3. Criar o administrador local (uso exclusivo de desenvolvimento; nunca reutilize senha de produção)
python manage.py createsuperuser

# 4. Ligar o servidor de desenvolvimento do Django
python manage.py runserver

# O painel administrativo responde em http://127.0.0.1:8000/<ADMIN_URL> — e não mais em /admin/.

Passo 4.4: Atualizar dependências e revisar o primeiro commit

# 1. Atualizar o registro de dependências (se instalou algo novo desde o Passo 2.4)
pip freeze > requirements.txt

# 2. Revisar o que será versionado. Em repositório novo o "git diff" simples não mostra arquivos
#    ainda não rastreados; por isso revise com "git status" e, depois do "git add", com "git diff --staged".
git status
git add .
git status
git diff --staged

# ⚠️ Confirme que .env, .venv/ e db.sqlite3 NÃO aparecem na lista de arquivos a commitar.

# ⚠️ NOTA SOBRE O PRIMEIRO COMMIT: o primeiro commit de um repositório vazio é o que cria a "main".
# O padrão (Doc ① §6.1) proíbe commits diretos na main e não descreve esse caso inicial. Faça o
# commit inicial somente após o checklist da seção "Ao Iniciar um Projeto Novo" e com autorização
# explícita do responsável humano; um agente de IA não deve executá-lo por iniciativa própria (§7.6).
# git commit -m "chore(setup): estrutura inicial do projeto Django"
# Depois do commit inicial, todo o trabalho segue em branches (PARTE 5).

e também o Passo 2.1 (ambos são feitos uma única vez por máquina). Bastará começar direto no Passo 2.2, alterando

                               └── 📂 apps/ (Apps modulares)
                                    ├── 📂 core/ (UUIDModel e utilitários) + README.md
                                    └── 📂 accounts/ (Usuário com UUID, RBAC, login) + README.md

...


Para clonar um projeto existente do Git mantendo essa mesma estrutura de isolamento (Windows/WSL), o fluxo muda um pouco porque o código do projeto já existe e vem do repositório. Você não precisa rodar o django-admin nem configurar o .gitignore do zero, mas precisará recriar os arquivos locais ocultos (.venv e .env) que foram barrados pelo Git por segurança. Aqui está o roteiro complementar focado exclusivamente em clonagem:

📥 Roteiro para Clonar Projetos Django no WSL
🐧 No Terminal do Ubuntu/WSL
Abra o aplicativo Ubuntu no menu iniciar do Windows. 

Todos os comandos abaixo devem ser executados no terminal Linux.

Passo 1: Entrar na pasta do ecossistema Django e clonar
Navegue até o diretório do ecossistema Django e baixe o repositório desejado (substitua a URL pela do seu projeto):

# 1. Ir para a pasta do ecossistema Django
cd ~/projetos/django

# 2. Clonar o projeto (Isso criará automaticamente a pasta Django_projeto_XYZ)
git clone https://github.com/usuario/Django_projeto_XYZ.git

# 3. Entrar na pasta recém-criada pelo Git
cd Django_projeto_XYZ

# 4. Conferir a identidade do Git (Doc ① §5.3)
git config user.email
# O endereço DEVE conter users.noreply.github.com. Se vier vazio ou com e-mail pessoal, pare e corrija
# (Passo 2.1) antes de qualquer commit. Não configure um e-mail pessoal para "resolver" a ausência.


Passo 2: Recriar o Ambiente Virtual Local
Como a pasta .venv nunca vai para o GitHub, você precisa construir uma nova versão dela dentro desta máquina Linux:

# 5. Criar o Ambiente Virtual local usando o Python do Linux
python3 -m venv .venv

# 6. Ativar o ambiente virtual
source .venv/bin/activate


Passo 3: Instalar as Dependências do Projeto
Em vez de instalar os pacotes manualmente um a um, você usará o arquivo requirements.txt que veio no repositório para baixar tudo nas versões exatas:

# 7. Atualizar o pip e instalar todos os pacotes da lista
pip install --upgrade pip
pip install -r requirements.txt


Passo 4: Criar o arquivo .env local

O arquivo .env original também foi barrado pelo Git para não expor senhas. 

Você precisa criar um arquivo novo na raiz deste projeto clonado:

# ATENÇÃO: antes de preencher os valores, verifique se existe um arquivo .env.example na raiz do
# projeto — ele lista os nomes das variáveis exigidas. Nunca adivinhe variáveis, nunca copie o .env
# de outro projeto e nunca use credenciais de produção em ambiente local (Doc ① §3.4).

# 8. Consultar os nomes das variáveis exigidas
cat .env.example

# 9. Criar o .env físico local a partir do modelo (o .env.example não contém valores reais)
cp .env.example .env

# 10. Gerar uma SECRET_KEY nova e exclusiva para este clone (nunca reaproveite o exemplo):
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"

# Abra o .env (ex.: code .env), cole a chave gerada em SECRET_KEY e ajuste, para uso LOCAL:
#   DEBUG=True
# As demais variáveis (ADMIN_URL, DB_PASSWORD, chaves de API etc.) devem ser obtidas da documentação do
# projeto ou do próprio .env.example. FIELD_ENCRYPTION_KEY e JWT_SIGNING_KEY, quando exigidas, são
# geradas localmente e distintas entre si e da SECRET_KEY (Doc ① §18.4).
# Se NÃO existir .env.example, não invente as variáveis: peça a lista ao responsável pelo projeto.

# NOTA: Se o criador do projeto tiver deixado variáveis extras (como DB_PASSWORD),
# você precisará adicioná-las aqui também (verifique o .env.example, se existir).


Passo 5: Migrações, Branch de Trabalho e Servidor

# 11. Abrir o projeto no VS Code do Windows conectado ao WSL
code .

# 12. Diagnóstico de migrações (somente verifica; NÃO cria arquivos)
python manage.py makemigrations --check --dry-run
# "No changes detected" é o resultado esperado em um clone. Se listar alterações pendentes, NÃO gere
# migrações por conta própria: informe o responsável pelo projeto (Doc ① §7.6).

# 13. Executar as migrações versionadas no repositório, criando o banco local (SQLite)
python manage.py migrate

# 14. Criar o administrador local (uso exclusivo de desenvolvimento; senha nunca reutilizada)
python manage.py createsuperuser

# 15. Verificar a branch antes de alterar qualquer arquivo
git status
git branch
# Para apenas executar o projeto, nada é alterado. Se for desenvolver, crie a branch de trabalho antes de
# editar (PARTE 5, Cenário B). Nunca desenvolva diretamente na main.

# 16. Ligar o servidor de desenvolvimento
python manage.py runserver
# Se o projeto usa ADMIN_URL, o painel administrativo responde em /<ADMIN_URL> e não em /admin/.

🔍 Resumo visual de como a clonagem funciona na prática:

☁️ GitHub (Contém apenas o código puro)
 │    ├── 📂 meu_site/ (Código Django)
 │    ├── 📂 apps/ (Apps modulares, com migrações versionadas)
 │    ├── 📄 manage.py
 │    ├── 📄 .env.example (Nomes das variáveis exigidas, sem valores)
 │    └── 📄 requirements.txt (Receita de quais pacotes instalar)
 │
 ⬇️ (git clone em ~/projetos/django/)
 │
🐧 Seu Ambiente WSL 2 (Gera o que estava oculto localmente)
      ├── 📦 .venv/ (Criado localmente pelo Passo 2 e alimentado pelo Passo 3)

      └── 🗄️ db.sqlite3 (Criado localmente pelo "migrate" do Passo 5)

Como os projetos que você vai clonar já possuem a PARTE 3 (as linhas do django-environ no topo do settings.py), 
assim que o servidor do Passo 5 (comando 16) subir, ele vai ler o seu .env local imediatamente!

🌿 PARTE 5: Rotina Diária de Desenvolvimento e Controle Git (Branching, Commits e Sync)

Utilize este fluxo contínuo para gerenciar seu trabalho diário com segurança, garantindo que tarefas em andamento sejam preservadas e novas tarefas iniciem a partir do código mais recente.

---

Passo 5.1: Início do Dia — Identificação e Preparação do Ambiente

Toda vez que abrir o terminal para programar, siga estes 3 comandos iniciais:

# 1. Entrar na pasta do projeto e ativar o ambiente virtual
cd ~/projetos/django/meu_projeto_django
source .venv/bin/activate

# 2. Verificar o status atual e em qual branch você está
git status
git branch

# 3. Decidir o fluxo de trabalho do dia (Cenário A ou Cenário B abaixo):


======================================================================
CENÁRIO A: Retomando uma tarefa em andamento (Mesma branch de ontem)
======================================================================

Se você já estava trabalhando em uma branch (ex: feat/modulo-produtos) e a funcionalidade ainda não acabou:

# 1. Certifique-se de estar na sua branch de trabalho
git checkout feat/modulo-produtos

# 2. (Opcional, mas recomendado) Trazer novidades que a equipe subiu na main sem sair da sua branch
#    (Doc ① §6.3: a atualização deve preservar suas alterações locais; em caso de conflito, pare e
#    siga o Passo 5.5 — não resolva com comandos destrutivos)
git pull origin main

# 3. Abra o editor e continue programando normalmente
code .


======================================================================
CENÁRIO B: Iniciando uma funcionalidade NOVA do zero
======================================================================

Se a tarefa anterior já foi finalizada ou você está começando um recurso novo:

# 1. Voltar para a main limpa
git checkout main

# 2. Sincronizar com as últimas alterações do repositório remoto
git pull origin main

# 3. Criar e alternar para a nova branch seguindo o padrão Conventional Branches:
#    (feat/, fix/, refactor/, style/, docs/, test/, chore/)
git switch -c feat/modulo-produtos

# 4. Abra o editor para começar a programar
code .


---

Passo 5.2: Durante o Dia e Fim de Expediente — Staging e Commits Semânticos

Sempre que concluir uma etapa lógica ou ao final do dia de trabalho (para fazer o salvamento diário):

# 1. Verificar os arquivos modificados
git status

# 2. Revisar as alterações feitas
git diff

# 3. Adicionar as alterações à área de preparação (staging)
git add .

# ⚠️ Verificação de segurança: rode "git status" e confirme que .env e .venv NÃO constam na lista.

# 4. Conferir a identidade do Git antes de commitar (Doc ① §5.3)
git config user.email
# Deve conter users.noreply.github.com.

# 5. Registrar o commit seguindo o padrão Conventional Commits:
#    Estrutura: tipo(escopo-opcional): descrição no imperativo
git commit -m "feat(produtos): implementa listagem e filtro de busca"


---

Passo 5.3: Envio para o Repositório Remoto (Push / Backup Diário)

Envie seu progresso para o GitHub para manter o código seguro na nuvem:

# Se for o primeiro envio desta branch para o GitHub:
git push -u origin feat/modulo-produtos

# Nos envios dos dias seguintes na mesma branch (salvamento diário):
git push


---

Passo 5.4: Conclusão da Funcionalidade, Pull Request e Limpeza

Execute este passo APENAS quando a funcionalidade da branch estiver 100% pronta e testada
(Definition of Done do PROJECT_SPEC.md §12):

1. Acesse o GitHub no navegador e abra um **Pull Request (PR)** da sua branch (`feat/modulo-produtos`) para a `main`.
2. Faça a revisão humana e confirme o **Merge** do Pull Request no GitHub (Doc ① §6.7 e §7.3).
3. No terminal WSL, sincronize o ambiente local e remova a branch concluída:

# 1. Retorne para a branch principal
git checkout main

# 2. Puxe a versão final integrada
git pull origin main

# 3. Exclua a branch de trabalho local que já foi mesclada
git branch -d feat/modulo-produtos

# 4. Sincronizar referências locais com o GitHub (remove ramos já deletados remotamente)
git fetch --prune

Passo 5.5: Trabalhando com um Agente de IA (resumo das salvaguardas — Doc ① §7)

Este passo é um resumo narrativo. As regras vinculantes estão no Doc ① (AGENT_INSTRUCTIONS_DJANGO.md §7 e §26).

1. Capacidade técnica não é autorização (§7.1): o agente segue as regras mesmo podendo ignorá-las.

2. Protocolo de plano e confirmação, a cada nova tarefa (§7.6). O agente deve:
   - ler o Doc ①, o PROJECT_SPEC.md, o regras_de_negocio.md e os README.md das apps afetadas;
   - apresentar um plano detalhado (arquivos afetados, migrações, dependências novas, riscos, testes);
   - aguardar a sua confirmação explícita — sem ela, apenas lê e analisa (não cria nem altera arquivos,
     não instala pacotes, não gera nem aplica migrações);
   - comunicar em português e, ao final, reportar o que foi feito, os testes e as pendências.
   Você pode dispensar o plano prévio de uma tarefa de forma explícita, mas isso nunca afrouxa o item 3.

3. Comandos que exigem confirmação explícita e NUNCA são executados por iniciativa do agente (§7.2):
   git push --force / -f / --force-with-lease, git reset --hard, git clean -fd, git branch -D,
   git push origin --delete <branch>, git rebase, git commit --amend.
   Antes de qualquer um deles o agente explica o que o comando faz, a consequência e pede confirmação.

4. Arquivos locais protegidos (§7.5): não excluir sem confirmação .env, db.sqlite3 e .venv/ — mesmo que
   a exclusão pareça resolver um problema de ambiente.

5. Erros e conflitos Git (§7.4): preservar o estado atual, informar o erro, apresentar opções e aguardar
   orientação. Sem resolução automática com comandos destrutivos.

6. Dependências novas (§7.7): só entram com finalidade, alternativa em biblioteca padrão e impacto de
   segurança constando no plano aprovado; atualizam o requirements.txt no mesmo commit (chore(deps)).

7. Pull Requests (§7.3): o agente não aprova nem faz merge sem revisão humana.

📘 PARTE 6: Guia de Fluxos Django — Clonagem × Criação do Zero (resumo comando a comando)

Origem: este bloco incorpora, na versão 3.1, o documento "GUIA DE FLUXOS DJANGO: CLONAGEM VS. CRIAÇÃO DO
ZERO". Ele é uma visão em lista, com uma explicação curta por comando; os procedimentos detalhados estão
nas PARTES 2 a 5 e no "Roteiro para Clonar Projetos Django no WSL".

Legenda das marcas usadas nos passos abaixo:
  [ORIGINAL]    passo mantido como estava no guia original
  [AJUSTE v3.1] passo do guia original alterado para ficar de acordo com o Doc ① v3.1
  [NOVO v3.1]   passo que não existia no guia original e passou a ser exigido pelo Doc ① v3.1

Todos os comandos são executados no terminal Ubuntu/WSL 2 (nunca em PowerShell, nunca em /mnt/c/).

===============================================================================
FLUXO 1: A PARTIR DE UM REPOSITÓRIO EXISTENTE (CLONE)
===============================================================================
Cenário: Você baixou um projeto já existente (GitHub/GitLab) e precisa preparar
o ambiente local e colocar a aplicação para rodar.

1. cd ~/projetos/django                                                  [NOVO v3.1]
   -> Entra na pasta do ecossistema Django, no filesystem nativo do WSL. Nunca clone soltos em
      ~/projetos/ nem em /mnt/c/ (Doc ① §2.1 e §3.3).

2. git clone https://github.com/usuario/nome-do-repositorio.git         [ORIGINAL]
   -> Baixa todos os arquivos, pastas e histórico do repositório remoto para a sua máquina.

3. cd nome-do-repositorio                                                [ORIGINAL]
   -> Entra no diretório raiz do projeto recém-clonado.

4. git config user.email                                                 [NOVO v3.1]
   -> Confere a identidade do Git (Doc ① §5.3): o endereço deve conter users.noreply.github.com. Se vier
      vazio ou com e-mail pessoal, pare e corrija antes de qualquer commit.

5. python3 -m venv .venv                                                 [ORIGINAL]
   -> Cria o diretório de ambiente virtual isolado (.venv) para que as bibliotecas
      do projeto não interfiram no Python global do sistema operacional.

6. source .venv/bin/activate                                             [AJUSTE v3.1]
   -> Ativa o ambiente virtual (.venv) no terminal do WSL/Ubuntu. A partir deste comando, qualquer
      comando "pip" instalará pacotes exclusivamente dentro da .venv, e o prompt passa a exibir (.venv).
      (Ajuste: removidas as menções a PowerShell e macOS, pois o desenvolvimento ocorre apenas no WSL 2.)

7. pip install --upgrade pip                                             [ORIGINAL]
   -> Atualiza o gerenciador de pacotes pip para garantir compatibilidade com as
      versões mais recentes das dependências.

8. pip install -r requirements.txt                                       [ORIGINAL]
   -> Lê a lista de bibliotecas e versões especificadas no arquivo requirements.txt
      e instala todas elas automaticamente no ambiente virtual.

9. cat .env.example                                                      [NOVO v3.1]
   -> Mostra os nomes das variáveis que o projeto exige (Doc ① §3.4). Nunca adivinhe variáveis. Se o
      arquivo não existir, peça a lista ao responsável pelo projeto em vez de inventá-la.

10. cp .env.example .env                                                 [AJUSTE v3.1]
    -> Cria o arquivo local de variáveis de ambiente a partir do modelo versionado (sem valores reais).
       Para uso local, DEBUG=True. Nunca copie o .env de outro projeto e nunca use credenciais de produção.
       (Ajuste: o guia original dizia "ou crie manualmente caso não exista"; agora, sem .env.example,
       não se inventam variáveis.)

11. python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"   [NOVO v3.1]
    -> Gera uma SECRET_KEY nova e exclusiva para este clone; cole o valor no .env (Doc ① §3.4).

12. python manage.py makemigrations --check --dry-run                    [AJUSTE v3.1]
    -> Apenas verifica se os modelos (models.py) estão em dia com as migrações existentes, sem criar
       arquivos. "No changes detected" é o esperado. (Ajuste: o guia original rodava "makemigrations",
       que em um clone gera migrações novas e divergentes do repositório. Em clone, as migrações já
       vêm versionadas; se houver alterações pendentes, avise o responsável — Doc ① §23.2 e §7.6.)

13. python manage.py migrate                                             [ORIGINAL]
    -> Executa as migrações pendentes, criando ou atualizando as tabelas e índices
       na base de dados local (ex: db.sqlite3).

14. python manage.py createsuperuser                                     [ORIGINAL]
    -> Cria um usuário com privilégios de administrador para autenticação e gestão
       completa no painel administrativo. Uso exclusivo local: não reutilize senha de produção.

15. git status && git branch                                             [NOVO v3.1]
    -> Verifica a branch de trabalho (Doc ① §23.2). Para apenas executar o projeto, nada é alterado. Para
       desenvolver, crie a branch antes de editar qualquer arquivo; nunca trabalhe diretamente na main.

16. python manage.py runserver                                           [AJUSTE v3.1]
    -> Inicia o servidor embutido de desenvolvimento do Django, disponibilizando a
       aplicação para testes locais geralmente em http://127.0.0.1:8000/. O painel administrativo responde
       em /<ADMIN_URL> quando o projeto segue o padrão (Doc ① §11.3), e não em /admin/.


===============================================================================
FLUXO 2: CRIAÇÃO DE UM PROJETO NOVO DO ZERO
===============================================================================
Cenário: Você não possui código prévio e vai iniciar uma aplicação Django
do absoluto zero em uma pasta limpa.

1. mkdir -p ~/projetos/django/meu_projeto && cd ~/projetos/django/meu_projeto   [AJUSTE v3.1]
   -> Cria um novo diretório com o nome do seu projeto, dentro do ecossistema Django, e entra
      imediatamente nele (Doc ① §2.1). Nunca solto em ~/projetos/ nem em /mnt/c/.

2. python3 -m venv .venv                                                 [ORIGINAL]
   -> Inicializa a estrutura de um ambiente virtual isolado (.venv) dentro da pasta.

3. source .venv/bin/activate                                             [ORIGINAL]
   -> Ativa o ambiente virtual no terminal para isolar as futuras instalações.

4. pip install --upgrade pip                                             [ORIGINAL]
   -> Atualiza a versão do pip dentro da venv recém-criada.

5. pip install django django-environ argon2-cffi                         [AJUSTE v3.1]
   -> Baixa e instala o framework Django (PyPI) junto com o conjunto-base do ecossistema:
      django-environ (leitura tipada do .env) e argon2-cffi (hasher Argon2id) — Doc ① §22.2.
      (Ajuste: o guia original instalava só o Django e citava django-environ e djangorestframework como
      extras. Agora os dois primeiros são obrigatórios; pacotes extras, como djangorestframework, só entram
      com justificativa no plano — Doc ① §7.7.)

6. django-admin startproject meu_site .                                  [AJUSTE v3.1]
   -> Cria a estrutura fundamental do Django (manage.py e a pasta de configurações "meu_site").
      O ponto (.) no final é crucial: faz com que os arquivos sejam criados na raiz da pasta
      atual, evitando pastas aninhadas desnecessárias (ex: meu_projeto/meu_projeto/).
      (Ajuste: o guia original usava "core" como nome do pacote de configuração. "core" é o nome da app
      transversal do ecossistema (apps/core, Doc ① §9.4); use outro nome, como "meu_site".)

7. git init -b main                                                      [NOVO v3.1]
   -> Inicializa o repositório Git na raiz do projeto (Doc ① §23.1).

8. Criar o .gitignore (conteúdo completo: PARTE 2, Passo 2.4)            [NOVO v3.1]
   -> Antes de qualquer "git add". Conjunto mínimo: .venv/, .env, *.pyc, __pycache__/, *.log, .DS_Store,
      media/, staticfiles/ — mais db.sqlite3 quando o banco local for SQLite (Doc ① §4.7).

9. Criar o .env.example (conteúdo: PARTE 2, Passo 2.4)                   [NOVO v3.1]
   -> Arquivo versionado com os NOMES das variáveis, sem valores reais (Doc ① §4.6). Atualize-o no mesmo
      commit em que uma variável nova for adicionada.

10. Criar o .env local com uma SECRET_KEY nova (PARTE 2, Passo 2.4)      [NOVO v3.1]
    -> Arquivo local, protegido pelo .gitignore, com SECRET_KEY gerada para este projeto, DEBUG=True e
       ADMIN_URL (Doc ① §4.3 e §11.3). Nunca versionar.

11. pip freeze > requirements.txt                                        [ORIGINAL]
    -> Registra o nome exato e a versão de todos os pacotes instalados na venv dentro de um
       arquivo de texto, viabilizando que outros desenvolvedores possam reproduzir o ambiente.
       Repita este comando sempre que instalar uma dependência nova, no mesmo commit (chore(deps)).

12. Editar meu_site/settings.py: django-environ + baseline de segurança  [NOVO v3.1]
    -> Leitura tipada de SECRET_KEY e DEBUG, ALLOWED_HOSTS, cookies, HSTS, cabeçalhos e limites de entrada
       (PARTE 3; Doc ① §4.4 e §12.3). Remova as linhas originais de SECRET_KEY, DEBUG e ALLOWED_HOSTS.

13. mkdir -p apps/core apps/accounts && touch apps/__init__.py           [NOVO v3.1]
    -> Cria o pacote apps/, onde ficam todas as apps do projeto (Doc ① §9.2).

14. python manage.py startapp core apps/core                             [AJUSTE v3.1]
    python manage.py startapp accounts apps/accounts
    -> Cria a estrutura modular das duas apps-base (models, views, admin, apps). Em cada apps.py use
       name = 'apps.core' / 'apps.accounts' e adicione 'apps.core' e 'apps.accounts' à lista INSTALLED_APPS
       em meu_site/settings.py. Cada app tem um README.md obrigatório (Doc ① §9.3).
       Apps de domínio do produto (o "meu_app" do guia original) seguem o mesmo padrão, depois destas:
       mkdir -p apps/meu_app && python manage.py startapp meu_app apps/meu_app
       (Ajuste: o guia original criava "meu_app" na raiz do projeto, fora de apps/.)

15. Criar UUIDModel, o usuário customizado, AUTH_USER_MODEL e Argon2id   [NOVO v3.1]
    -> UUIDModel em apps/core, User(UUIDModel, AbstractUser) em apps/accounts, AUTH_USER_MODEL =
       'accounts.User', PASSWORD_HASHERS com Argon2id primeiro e ADMIN_URL no urls.py (PARTE 4, Passos 4.1
       e 4.2; Doc ① §10.4, §16.1 e §23.4). ⚠️ Precisa existir ANTES da primeira migração.

16. Copiar o PROJECT_SPEC.md (Doc ②) para a raiz; criar regras_de_negocio.md [NOVO v3.1]
    -> O PROJECT_SPEC.md é um modelo a preencher; o regras_de_negocio.md concentra RF/RN. Ambos são
       obrigatórios em cada projeto (Doc ① §24).

17. python manage.py makemigrations                                      [NOVO v3.1]
    -> Gera a migração inicial do usuário customizado (apps/accounts/migrations/0001_initial.py), que deve
       ser versionada. É necessário porque a app accounts ainda não possui migrações.

18. python manage.py migrate                                             [AJUSTE v3.1]
    -> Aplica as tabelas padrão e fundamentais do Django (tabelas de sessão, usuários,
       permissões e log do admin) na base de dados inicial (db.sqlite3).
       (Ajuste: só roda depois dos passos 12 a 15 e 17. Antes desta versão ele era o primeiro comando
       após o startproject, o que impedia trocar o modelo de usuário depois sem custo.)

19. python manage.py createsuperuser                                     [ORIGINAL]
    -> Cadastra o login e senha do administrador principal do sistema para acesso ao admin.

20. python manage.py runserver                                           [AJUSTE v3.1]
    -> Sobe o servidor web de desenvolvimento local na porta padrão 8000. Painel administrativo em
       /<ADMIN_URL> (Doc ① §11.3).

21. pip freeze > requirements.txt; git status; git add .; git status; git diff --staged   [NOVO v3.1]
    -> Atualiza as dependências, revisa o que será versionado e confirma que .env, .venv/ e db.sqlite3 não
       estão no staging (Doc ① §6.4 e §23.1). O primeiro commit exige autorização explícita do responsável
       (nota do Passo 4.4); depois dele, todo trabalho segue em branches.

Checklist de Segurança e Validação de Ambiente

(Versão 3.1: realinhado aos checklists do Doc ① §23.1 a §23.5. Em caso de divergência, vale o Doc ①.)

1. Ao Iniciar um Projeto Novo (Setup Inicial) — Doc ① §23.1

Antes do primeiro commit:

Isolamento de Diretório:
- [ ] Projeto localizado em ~/projetos/django/<nome_do_projeto>/ e armazenado no filesystem nativo do WSL — nunca solto na raiz de ~/projetos/ e nunca dentro de /mnt/c/ — para manter a performance e as permissões nativas.
- [ ] Repositório Git inicializado no diretório do projeto.

Ambiente Virtual Ativo:
- [ ] .venv criado na raiz do projeto e ativado (source .venv/bin/activate) antes de rodar qualquer pip install.
- [ ] Django instalado no ambiente virtual; django-environ instalado.

Proteção do .gitignore:
- [ ] .gitignore criado antes de qualquer git add, listando ao menos .venv/, .env, *.pyc, __pycache__/, *.log, .DS_Store, media/ e staticfiles/ (e db.sqlite3 se o banco local for SQLite).
- [ ] .env e .venv protegidos pelo .gitignore.
- [ ] git status executado para confirmar que nenhum arquivo confidencial ou binário está listado como staged ou untracked.

Configuração de Variáveis de Ambiente:
- [ ] settings.py preparado para variáveis de ambiente, com conversão tipada de booleanos: DEBUG = env.bool('DEBUG', default=False).
- [ ] .env criado localmente, com SECRET_KEY gerada exclusivamente para este projeto e DEBUG=True.
- [ ] .env.example criado, versionado e sem valores reais.
- [ ] Nenhuma string hardcoded de senhas ou tokens no settings.py.

Identidade do Git:
- [ ] git config user.email retorna o alias mascarado no-reply (ID+seu-usuario@users.noreply.github.com).

Dependências Congeladas:
- [ ] Dependências registradas em requirements.txt (pip freeze > requirements.txt) para documentar as versões exatas.

Revisão final:
- [ ] git status revisado.
- [ ] git diff (ou git diff --staged) revisado.
- [ ] Nenhum segredo está no staging.

2. Ao Clonar um Projeto Existente — Doc ① §23.2

Antes de executar o projeto:

- [ ] Repositório clonado em ~/projetos/django/<nome_do_projeto>/.
- [ ] .venv recriado localmente e ativado.
- [ ] requirements.txt instalado.
- [ ] .env.example consultado.
- [ ] .env recriado localmente.
- [ ] SECRET_KEY nova gerada para o ambiente local.
- [ ] Nenhuma credencial de produção utilizada.
- [ ] Variáveis adicionais identificadas.
- [ ] Migrações executadas conforme necessidade do projeto (sem gerar migrações novas por conta própria).
- [ ] Git configurado corretamente (git config user.email com o alias no-reply).
- [ ] Branch de trabalho verificada.

3. Na Continuidade do Desenvolvimento (Rotina Diária) — Doc ① §23.3

Antes de trabalhar:

- [ ] Ambiente virtual ativo: confirmar a tag (.venv) no início da linha do terminal antes de rodar scripts Python, migrações ou inicializar o servidor.
- [ ] Diretório correto (~/projetos/django/<nome_do_projeto>/).
- [ ] Branch correta (git branch): feat/..., fix/... — nunca alterando código diretamente na main.
- [ ] git status verificado.

Antes de commit:

- [ ] git status executado antes de qualquer git add . para garantir que o .env não foi renomeado, movido ou exposto acidentalmente.
- [ ] git diff executado: revisar as linhas alteradas para garantir que logs com dados sensíveis, senhas de teste ou prints de depuração não sejam enviados ao histórico.
- [ ] .env e .venv não estão no staging.
- [ ] Tokens e senhas não estão no código; novas credenciais (chaves de API, acessos a banco) foram para o .env e não direto no código-fonte.
- [ ] Logs de depuração não serão persistidos indevidamente; dados sensíveis não foram adicionados.
- [ ] Novas variáveis de ambiente estão no .env.example, no mesmo commit.
- [ ] Integridade de dependências: se novos pacotes foram instalados via pip durante a sessão, o requirements.txt foi atualizado imediatamente (pip freeze > requirements.txt).
- [ ] Commit segue Conventional Commits.

Antes de merge:

- [ ] Branch publicada e Pull Request criado.
- [ ] Alterações revisadas e testes apropriados ao projeto executados.
- [ ] Revisão humana realizada e merge autorizado.
